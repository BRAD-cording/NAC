## 0. 裁决（TL;DR）

**当前状态不可投稿，且不是"改写能救"的问题，而是"证据基础需重建"。**

三条致命结论：

1. **板端 GSM8K 的全部"崩塌"（0.005 / 0.010 / 0.015 / 0.025）是 32-token 生成上限造成的截断伪影，不是量化退化。** 同一厂商模型在 32 token 下同样是 0.0000（200 题），在 512 token 下是 0.5550。被引为"灾难"的 NAC 板端 0.005 的存档生成，全部是**连贯、正确开头、在 138 字符处被硬截断的思维链**，没有任何"数值错乱"形态。这一条同时废掉 Table 1、C2（zp 重解释）、E3 对照、R3–R4 全部 bisect 判别，以及以 `p=7.08e-25` 表述的板端统计。
   **2026-10-30 补测闭环**：四个产物的 32→512 对照——厂商 0.0000→0.5550；本地重建 0.0150→**0.5350**（p=0.69）；组量化构建（曾被当作"NAC 崩塌"证据）0.0050→**0.5650**（p=0.88）；第二个组量化构建 0.0050→**0.5600**（p=1.00）。三个处理臂的 answer-is 与末数字指标完全相同，唯一变量是生成上限，分数差 52–56pp——伪影判定已无可争议。
1b. **更糟：Table 1 的 NAC / E3 / NAC-v2 三行是同一个字节文件**（md5 全为 `3bd8c0ba…`，实测确认）。处理组从未存在，"对照实验"是自比自（§2.6）。
1c. **而且处理组与对照组的量化 dtype 不同**：三个"注入"构建是 `W4A16_G64`，厂商与本地构建是 `W4A16`（per-channel）。组粒度这个未受控变量使任何"NAC vs 基线"的分数差都无法归因（§2.7）。
2. **归档不可审计**：所有历史评分的 records 都把生成截断存档（sim 300 字符、板端 200 字符），且不落 `n_tokens` / EOS / `max_new_tokens`。评分用的是推理时全文——**论文里没有任何一个 GSM8K 数字能被第三方从归档复现**。这是 Q1 的硬性否决项。
3. **抽取规则是一阶混杂**：`last-number` 与 `answer-is` 两种规则把五个方法的 GSM8K 从 0.07–0.31 全体抬到 0.30–0.39，把 E2 的"GPTQ 4× 优势"压缩到 1.1×，并把 AWQ 的"0.000 灾难"变成 0.359。C3 的**方向**（PPL 不预测长程生成）可能仍成立，但**幅度叙事（AWQ 归零）不成立**。

两条结构性问题（即使上面全部修好也仍在）：

4. **单平台 + 单模型族**（RK3576 / Qwen2.5-1.5B），且板端修复从未验证。JCR Q1 主流刊（TCAD/TPDS/FGCS/JSA 等）几乎必然要求第二平台或第二模型族，或一个机制级的硬件证据。
5. **"首次系统评测"主张与现有文献冲突**：`Accuracy is Not All You Need`（NeurIPS'24）已系统论证"精度不足以评价压缩模型"；Ascend NPU 上已出现 PTQ 基线研究（arXiv 2602.17693）。"PPL 与下游脱钩"不是新发现，本文只能主张"在 NPU 部署栈上、对长程生成、给出机制与边界"。

**Q1 可行性判断**：**条件性可行，但不是当前这条叙事**。以现有最强证据（sim 轴五方法矩阵 + g128 反转 + 校准目标消融）为骨架，补齐 fp16 锚点、双指标、终止行为分析、第二模型族，可冲 JCR Q1（FGCS/JSA/Neural Networks 一档）；TCAD/TPDS 需要机制级硬件证据，当前不具备。TMLR 是可退守选项（非 JCR Q1）。

## 2. 致命问题 F1：板端 GSM8K 崩塌是 32-token 截断伪影

### 2.1 决定性对照：同一模型，32 vs 512

| 运行 | 模型 | max_new_tokens | GSM8K zs (200) | 存档长度 p50 |
|---|---|---|---|---|
| `acc_gsm8k_qwen1.5b_w4a16_zs32` | 厂商预转 w4a16 | **32** | **0.0000** | 140 字符 |
| `acc_gsm8k_qwen1.5b_w4a16_zs` | 同一模型 | 512 | **0.5550** | 200（归档截断） |

**同一份权重、同一套题、同一评测代码，唯一差别是生成长度上限，分数从 0.555 掉到 0.000。** 这是"协议决定结论"的直接证明。而 outline 的 Table 1 恰恰是拿 **512-token 的厂商基线 0.5550** 去比 **32-token 的 NAC 0.0050**，再把差异解释为"NPU 对 float-zp 的重解释"。

**同一产物级的第二组对照（2026-10-30 补测，最干净的一条证据）**：

| 产物 | @32 tok | @512 tok |
|---|---|---|
| 厂商 W4A16 | 0.0000 | 0.5550 |
| 本地重建（normal, opt1, W4A16） | 0.0150 | **0.5350** |
| 组量化构建（W4A16_G64，曾被当作"NAC 崩塌"证据） | 0.0050 | **0.5650** |

本地构建在 512-token 下与厂商**统计平手**（配对 McNemar p=0.69）；组量化构建同样平手（0.5650 vs 0.5550，p=0.88），且其末数字与 answer-is 指标完全相同（0.5650/0.5650）——说明连"续写污染"都不存在。同一文件、同一题集、同一代码，唯一变量是生成长度上限，分数差 52–56 个百分点。至此"本地构建损伤长程推理"与"注入导致板端崩塌"两条假设链被彻底否定。

### 2.2 生成形态：不是数值错乱，是被截断的思维链

`acc_gsm8k_qwen1.5b_g64nac_zs.records.json` 第 0 题（gold=52）：

```
To find the average of the three measurements, we need to add Jared's typing speed
before the lessons and after the lessons, and then divide by 3.
```
（146 字符后终止；`pred=3.0`，因为末数字是 "3"。）

厂商模型 32-token 版第 0 题：

```
To find the average of the three measurements, we need to add the three measurements
together and then divide by 3.\n\nThe first measurement is 47 W
```
（146 字符后终止；`pred=47.0`。）

两者**完全同型**：开头正确、推理合理、在数字中间被硬切。TECHNICAL_REPORT §3.2 记载的失败模式"预测全为小数（'3.0'/'1.0'/'50.0'）、长度中位数 3"——"长度中位数 3"在现存归档中**不存在**（全部 p50≥102 字符），而"预测全为小数"正是"末数字抽取器 + 截断在数字中间"的必然产物，不是模型退化。

### 2.3 全部板端 GSM8K 运行呈同一签名

| 配置 | 存档 acc | p50 长度 | p90 | 末尾落在数字/运算符 | 含 "answer is" |
|---|---|---|---|---|---|
| vendor w4a16 @32 | 0.0000 | 140 | 160 | 0.32 | 0.00 |
| NAC-v1 注入 @32 | 0.0050 | 138 | 158 | 0.28 | 0.00 |
| E3 minmax 注入 @32 | 0.0050 | 138 | 158 | 0.28 | 0.00 |
| NAC-v2 int-zp 注入 @32 | 0.0050 | 138 | 158 | 0.28 | 0.00 |
| sym-minmax @32 | 0.0050 | 147 | 161 | 0.32 | 0.00 |
| asym-minmax @32 | 0.0100 | 142 | 159 | 0.27 | 0.00 |
| local plain x86 @32 | 0.0150 | 138 | 157 | 0.38 | 0.00 |
| R4-a/b/c/d @32 | 0.000–0.025 | 129–145 | 152–161 | 0.28–0.38 | 0.00 |

**11 个板端运行，无一例外**：长度顶在 32-token 的字符预算上（≈160），没有一条生成到"答案句"。这不是模型差异，是协议上限。

### 2.4 推论：被废掉的结论

| 被废结论 | 原证据 | 为什么废 |
|---|---|---|
| C2「NPU 重解释 float-zp，GSM8K 0.555→0.005」 | NAC@32 vs vendor@512 | 两臂协议不同；同协议下 vendor 也是 0.000 |
| E3「minmax float-zp 同崩 → 非 NAC 特有」 | mmctrl@32 = 0.005 | 对照与处理同为截断伪影，无判别力 |
| 「问题 A / 问题 B 双问题叠加」 | E2（sim）+ E3（板端） | 板端臂失效，仅剩 sim 单臂 |
| R3–R4 七连证伪（B1/B3/B5/B6/B7/B8/B2-gdq/grq） | 0.000–0.025 的"崩/不崩"判据 | 判据恒为崩，属对空判据 |
| 「本地构建路径病理」 | R3 plain 0.015 | 同为 32-token 伪影；本地构建在 512 下从未被测 |
| 板端统计 `p=7.08e-25` | stats_pairs `board_gsm8k::nacinject_vs_base` | 配对无效（协议不同），p 值无意义 |

**注**：10-29 深夜的 git 提交已发现一半（"32-token 截断伪影"），但把结论写成"真崩坏仍只有 E3 时代注入构建（512-token、中位 3 token）"，并据此**提升 R5 的重要性**。现存归档中不存在任何本地/注入构建的 512-token 板端运行，"中位 3 token"无落盘证据。该判断需撤回。

### 2.6 叠加致命：Table 1 的"处理组"根本不存在

本次评审对 `models/*.rkllm` 实测 md5：

| 模型文件 | 大小 | md5 | 被哪次评测使用 |
|---|---|---|---|
| `nac_qwen1.5b_g64_nac.rkllm` | 1,653,561,316 | **3bd8c0ba…** | `g64nac_zs`（Table 1 NAC 行） |
| `nac_qwen1.5b_g64_mmctrl.rkllm` | 1,653,561,316 | **3bd8c0ba…** | `g64mmctrl_zs`（Table 1 E3 行） |
| `nacv2_qwen1.5b_g64_intzp.rkllm` | 1,653,561,316 | **3bd8c0ba…** | `g64_nacv2intzp_zs`（板端 v2） |
| `sym_minmax_g64.rkllm` | 1,653,561,316 | **3bd8c0ba…** | （未评测） |
| `sym_minmax_g64_v2.rkllm` | 1,653,561,316 | d6ff154d… | `g64symminmax_zs` |
| 厂商基线 | 1,410,933,676 | 90330bf1… | 全部 baseline |

**NAC、E3 对照、NAC-v2 三个"不同处理"是同一个字节文件。** 这与 10-23 的记录一致（工具链日志 `0 extra qparams already found and loaded!`，注入从未生效），也与 MMLU 三者完全相同（0.5614）吻合。因此：

- Table 1 的第 2、3 行是**同一模型的两次测量**，"NAC vs E3 对照"是自比自；
- C2 的板端证据不是"弱"，而是**零**（没有 treatment，也没有有效协议）；
- 10-29 深夜"真崩坏只剩注入构建"的说法在此也不成立——所谓注入构建就是普通的 qemu 构建。

**同时暴露一个新问题**：注入构建 1.65 GB vs 原生构建 1.41 GB（+17%），说明两者**量化/打包配置不同**。这个差异从未被记录或控制，任何"注入 vs 原生"的对比都混入了构建配置差异。

**唯一的互异注入候选**是 `sym_minmax_g64_v2`（d6ff15），它在 32-token 下也是 0.005——需在 512-token 下复测才能判断它是否真的注入了、以及是否真的崩。字节 diff 显示它与 `3bd8c0ba` 有 42.1% 字节不同（两个区域：690.6–1315.4 MiB 权重区、1537.9–1577.0 MiB 尾部参数区），因此它确实是一个**不同的模型**，可作为"注入是否生效"的候选样本。

### 2.7 第二个未受控变量：量化 dtype 不同

从 runtime 日志逐条提取 `model_dtype`（38 条日志）：

| 产物族 | 日志中的 dtype | 大小 |
|---|---|---|
| 厂商预转基线 | **W4A16** | 1,410,933,676 |
| 本地 x86 构建（plain / R4-a…d） | **W4A16** | 1,410,933,676 / 1,294,257,260 |
| 三个"注入"构建（3bd8 族）+ symv2 | **W4A16_G64** | 1,653,561,316 |

也就是说：**被当作"NAC 处理组"的三个构建用的是 g64 分组量化，而对照组（厂商、本地构建）用的是 per-channel W4A16。** 这两者在量化粒度上就不同，1.65 GB vs 1.41 GB 的文件大小差正是 per-group scale 的开销。

后果：
- 即使 512-token 复测显示 3bd8 与厂商分数接近或不同，也**不能**归因于"校准方法"——组粒度是未受控变量；
- Table 1 的"vendor vs NAC"从来不是单变量对照；
- 唯一与厂商同 dtype 的本地构建是 R3/R4 族（W4A16），它们的 MMLU 0.4974–0.5387 与厂商 0.5583 的差距才是"构建路径"的干净估计（且仍需 512-token 复测才能谈 GSM8K）。

**修正后的板端对照设计**：所有臂必须 `quantized_dtype` 相同（建议统一 `w4a16_g64`，与部署目标一致），再变校准/算法；否则任何差异都无法归因。

### 2.8 哪些证据仍然成立（重要：不是全盘否定）

为避免"全错"的误读，本节列出经独立重算**通过**的部分：

| 检查 | 方法 | 结果 |
|---|---|---|
| sim MMLU 九配置 | 用 records 重算 `extract_choice` | 与 summary **逐位一致**（0.4634/0.4675/0.4520/0.3932/0.4469/0.4396/0.4871/0.3622/0.4293） |
| 板端 MMLU 六配置 | 同上 | 与 summary 逐位一致（0.5614/0.4974/0.5191/0.4974/0.5387/0.5583） |
| 抽取规则敏感性（MMLU） | 三种规则重算 | 最大差异 ≤1.1pp，**不是** MMLU 差距的来源 |
| 板端 MMLU 差距 | 同 dtype（W4A16）对比 | 本地 0.4974 vs 厂商 0.5583：**真实存在**的 6.1pp 构建路径差，不是伪影 |
| PPL 四配置 | 数值来源核对 | 文件自洽；未重跑（成本 64×1024 前向） |

**结论**：sim 轴的 MMLU/PPL/GSM8K summary、g128 边界、统计配对表都是可信的；失效的只有"板端 GSM8K 崩塌"这一条叙事链及其衍生的 C2/E3/bisect。这决定了 Q1 修订是"重写一条线"，不是"推倒重来"。

### 2.5 为什么此前 10 次评审都没抓到

1. **记录截断**：`gen[:600]`（旧）/`gen[:200]`（板端旧版）——评委看到的是被截断的生成，且不知道评分用的是全文。
2. **只看分数不看形态**：0.005 与 0.000 的差别被当成"崩坏程度"，而实际上是"末数字正好撞对一次"。
3. **协议字段缺失**：summary JSON 在 10-29 之前不落 `max_new_tokens`，无法从文件本身判定协议。
4. **文档层叠**：每轮审计在上一轮结论上增量，前一轮的错误前提被继承（outline §6.1 甚至明确写了"板端是 32-token 直答"并把它解释为"不同层级的失效"——问题被看见了，但被叙事吸收了）。

- **不可审计的"证据"不是证据**：Q1 期刊 reproducibility 要求（数据/代码/生成可获取）直接不满足。

### 4.2 对 C3 的影响

- **方向仍成立**：五方法在两种规则下的**排序**都保持"GPTQ 最好、minmax/AWQ 最差"，且 PPL 排序与 GSM8K 排序始终反向。这是 C3 唯一还站得住的部分。

## 5. 结构性问题（Q1 门槛）

### 5.1 单平台单模型族

全矩阵只有一个 SoC（RK3576）、一个模型族（Qwen2.5-1.5B）；3B 只有预转基线、无量化对照；NAC-v2 只有 1.5B。JCR Q1 系统类期刊的典型要求是"跨平台/跨模型验证"或"机制级硬件证据"。当前是**单点测量研究**，外推性不足。

### 5.2 缺 fp16 sim 锚点

Table 2 的 fp16 行 GSM8K 为"—"，即**没有"同栈、不量化"的长程生成参照**。后果：

- 无法回答"sim 栈本身是否就损伤长程生成"（sim fp16 MMLU 0.4634 vs 板端 0.5583 已有 9.5pp 栈差，说明 sim 栈本身有损）；
- GPTQ 0.305 是"量化损失"还是"栈损失 + 量化损失"不可分；
- C3（PPL 不预测长程）缺少上界锚点。

这是**低成本、高必要性**的补实验（一次 fp16 sim GSM8K，约 10–11 h）。

### 5.3 文献定位（"首次"主张）

- `Accuracy is Not All You Need`（NeurIPS 2024）已论证"压缩模型的精度指标不足以刻画行为"，本文若只主张"PPL/MMLU 不预测长程"会被判为重复。
- Ascend NPU 上的 PTQ 基线研究（arXiv 2602.17693）已覆盖"NPU 部署栈上的量化对照"。
- 因此本文的可辩护增量只能是：**(a) 在 W4A16 边缘 NPU 上把"模拟-部署语义差"做成可复现的判别实验；(b) 校准目标（激活加权 vs Hessian）对长程生成的影响机制；(c) 评测协议本身会反转结论的实证。** 三者中 (c) 是本次评审新发现、且有硬证据，但单独不足以支撑 Q1，需要与 (b) 合并。

### 5.4 硬件语义无直接证据

"NPU 对 float-zp 取整/重解释"这一核心机制，全项目**没有任何硬件级证据**（无寄存器/微基准/官方文档引用），只有"板端崩了 + 注入前 zp 非整数"的间接推断；而"板端崩了"已被证伪。**该机制目前是零证据的假说**，不得作为论文主线。

## 9. 修复路线（按阻断性）

### P0-a 板端 512-token 复测【已启动，v2 队列】

**先修正实验设计**：原计划跑 NAC-v1 / NAC-v2 / E3 三配置，但三者 `.rkllm` 的 md5 相同（§2.6），跑了也是同一个模型三次。v2 队列只跑三个**互异**产物：

|---|---|---|---|---|
| 1 | `nac_qwen1.5b_g64_nac.rkllm`（=3bd8，注入无效的 qemu 构建） | 3bd8c0ba | 该构建在 512 下是否健康 | ≈0.5 → 所谓"NAC 崩溃"彻底死；≈0 → 该构建本身有问题 |
| 2 | `sym_minmax_g64_v2.rkllm` | d6ff154d | 唯一互异的注入候选是否真的注入/是否真崩 | 与厂商配对 |
| 3 | 厂商基线 | 90330bf1 | 可审计的同协议锚点 | 应 ≈0.55 |

并行已完成：`local_w4a16_plain_x86`（x86 原生构建）@512 正在跑——它回答"本地构建是否真的崩"。

成本：3 × ≈2.5–3 h ≈ 8–9 h；已落新归档字段（全文/token/EOS）。**在出分前，正文不得引用任何板端 GSM8K 数字。**

**若要把 NAC 作为真正的板端 treatment**，必须先按 R5 用正确 schema（扁平 state-dict + 烘焙 int8）重建 1.5B 注入产物，并验证 md5 随 qparams 变化（R2 判据：`<N> extra qparams already found and loaded!` + 产物 md5 改变）。这一步没完成，板端 NAC 结论永远缺失。

### P0-a′ R5 重建方案（板端 treatment 的唯一出路）

**格式**（来自 tiny 探针 `gdq.qparams`）：扁平 state-dict
`{name.weight: int8∈[-8,7], name.weight_qscale: fp32(out, in/64), bias/layernorm: 原样 fp32}`，无独立 zp 键——zp 已烘焙进有符号 int8。

**步骤**：
1. 由 `results/nacv2_qwen1.5b_g64.qparams.pt`（scale, zp）算 `w_i8 = clamp(round(w/scale) - round(zp), -8, 7)`（整值 zp 下无损；非整 zp 会有 ≤1 个量化级的偏差，需记录）；
2. 生成 `weight_qscale = scale`，其余 fp 参数原样拷贝；
3. `r4a_build.py` 加 `extra_qparams=<新文件>`，其余参数与 R3 完全一致（单变量）；
4. 验收三判据：日志加载计数 = 196、产物 md5 ≠ `3bd8c0ba`、构建耗时显著短于 6h（命中缓存应跳过 Optimizing）。

**成本**：构建 ~15 min + export ~45 min ≈ 1 h（前提是 extra_qparams 命中）。**这是当前投入产出比最高的一步**：没有它，论文的板端轴只能写"未验证"。

**风险**：若 md5 仍是 `3bd8c0ba`，说明 schema 仍不对，需回到 tiny 探针重新对齐（R1 已走过一遍，1 天内可收敛）。

### P0-b sim 轴重跑（双指标 + 全文归档 + 停止条件）【已排队】

必须重跑：fp16（缺失）、GPTQ、minmax、NAC-v1、NAC-v2（AWQ 可选）。成本 ≈10.7 h/配置 × 4–5 ≈ 45–55 h。可压缩为 fp16 + GPTQ + NAC-v2 三配置（≈32 h），minmax/NAC-v1 用现有数字 + 敏感性分析标注。

**执行状态**：`scripts/q1_sim_queue.sh` 已部署并驻留，等 `results/q1_board512.DONE` 出现后自动依次跑 fp16 → GPTQ → NAC-v2，产物 `results/acc_gsm8k_sim_g64_stop_*.json`。

**新增设计要求（本次评审发现）**：2-shot CoT 前缀使所有方法都会在答完后继续写下一题（GPTQ 11%、min-max 38%、NAC-v1 30%、NAC-v2 37%、AWQ 53%），因此末数字抽取不只受截断影响，还受"续写多远"影响。重跑必须在评分前截断到第一个 `\nQuestion:`：

- **已实现**：`eval_gsm8k_sim.py --stop-strings` 采用后处理截断（截断点前文本参与抽取），并落 `stop_truncated` / `gen_raw_chars` 字段。
- **注意**：`transformers 5.18` 的 `generate()` **不支持** `stop_strings`（`inspect.signature` 返回 False，传参会静默忽略），因此不能用"生成时停止"，只能用后处理截断——这是冒烟验证时发现的，避免了 32 小时白跑。

两种做法都要在论文里写明；否则"校准质量"与"终止行为"仍然混在一起。建议同时报告 `hit_cap` 与 `answer_is`，把三个失效模式（算错 / 没答 / 不停）分开。

## 14. 预判审稿意见与应对（draft v0.1 口径）

按 Q1 审稿人最可能的攻击顺序排列。每条给出"不要说什么"和"应当怎么答"。

**O1「这只是测量，没有方法贡献。」**
答：确认为测量研究，且摘要末句明写不作 SOTA 主张。贡献是**可复现的判别协议** + 边界条件 + 构建可复现性结果；不声称新量化算法。风险中等——TMLR 接受，TCAD/TPDS 可能不接受。

**O2「NAC-v1/v2 不过是 AWQ/GPTQ 的变体。」**
答：同意，且正因如此才把它们当作"激活加权族 vs Hessian 族"的实例，而非新方法。论文的主张是"族间差异被 PPL 掩盖"，不是"NAC 更优"。

**O3「单平台、单模型，外推性不足。」**
答：承认并写入 Limitations。缓解：sim 轴五方法 × 两组粒度；部署侧结论限定在同一工件的重建差异。**不要**声称结论可推广到其他 SoC。

**O4「32-token 是稻草人，没人这么用。」**
答：本项目自己的评测脚本默认就是 32；更重要的是**同一篇论文里基线用 512、处理组用 32**——这才是问题。论点是"必须跑参考模型对照"，不是"32 很常见"。

**O5「answer-is 规则同样武断。」**
答：同意。所以报告两种规则并把结论限定在"两种规则下都成立"的部分；重跑用截断把终止与算术分离，不再依赖任一抽取规则。

**O6「PPL 与下游脱钩早有人说过。」**
答：引 *Accuracy Is Not All You Need* 与 Ascend PTQ 研究，明确增量是**机制**（终止决策/续写）+ **边界**（组粒度符号翻转），不是"发现相关性弱"。

**O7「板端根本没有 NAC 结果。」**
答：承认。注入在 1.5B 从未被证明生效（三个产物同 md5），因此不报板端 NAC；改报同 dtype 的构建路径差异（−6.09pp，p=3e-4；gdq 平手）。这是诚实性加分项，不是隐藏。

**O8「AWQ 只跑 64 题，统计不可比。」**
答：承认；只报 CI 不报点估计排序，且 AWQ 的作用是"第二方法族"的存在性证据，不是精确排名。

**O9「部署表里混了不同 dtype。」**
答：已显式排除 g64 产物并写出混杂（+6.40pp 不可归因），只保留 W4A16 五行。

**O10「为什么不用 MATH / 更长上下文？」**
答：GSM8K 已足够触发长程判别；MATH 与 LongBench 列为 future work，成本（板上数小时/题）在 Limitations 说明。

**共同底线**：任何一条被问到时，宁可缩小主张，也不要补一个未跑过的数字。本项目的全部事故都来自"文档里出现了没被数据支持的句子"。
